## R6 후속: 자동 세션 소유 지하철 관측 endpoint (부분 구현)

명시적 서버 opt-in에서만 관측 endpoint를 등록하고, 실제 JPA의 짧은 조회 전후 트랜잭션으로
로그인/개인 경로/준비 세션을 refresh한다. 취소·교체·로그아웃·경로 변경·만료 뒤의 열차
응답을 폐기하며 외부 I/O 중 DB 잠금을 유지하지 않는다. 공식 catalog 미설치 시 외부 조회는
0회다. 응답은 세션/구간에 묶인 열차 관측 개수이며 승객 탑승/위치/남은 역은 false/null이다.
BE 관련 최종 **16 suites/152 PASS**, FE **323 suites/3,169 PASS**, 타입 PASS.
후속 안내·교통·Live Activity 확장 회귀는 위 152건을 포함한 **81 suites/593 PASS**이며
격리 MySQL의 스키마 validate·재시작 후 END 단발 처리도 포함한다. 운영 DDL 재실행은 아니다.
Spring enabled/default-OFF 구성·실제 격리 H2 OSIV·실제 JWT 필터 경계도 검사했다.
같은 독립 시뮬레이터에서 신규 소유 세션 합성 **6사례**를 확인했다. 실제 공급자/GPS/APNs는
0회이며 제품의 실계정 HTTP→JPA→공급자 전체 E2E나 지하철 주행 증거가 아니다.
운영 재기동/배포/기본 ON/native 변경은 없다. 공식 운행 자료 설치·native 승객 결합과
지하철 상세/Activity·음성/알림·환승은 남았다.
[구현·실패 포함 자동 검사·독립 화면 결과](journey-owned-subway-observation-validation-20261013.md).

## R6 후속: 독립 역 대응·분기/급행 정차 순서 resolver

서버 소유 역 대응/운행 자료를 입력받는 bounded resolver를 구현했다. 저장 ODsay 원본의
전체 정차 순서를 독립 운행 순서와 정확히 대조하며, 이름·근접 좌표·ID 숫자 정렬·역순 복원은
사용하지 않는다. 분기 종착역은 후보를 분리하고, 같은 열차가 여러 패턴에 맞으면 차단한다.
중간 역 누락/반복 구간/과다 후보/고정 유효 기간 만료도 추측하지 않는다. 검증된 정차 목록은
Java/컬렉션 cast로도 변경할 수 없다. **공식 운영 데이터 설치·제품 지하철 탑승 판단 완료는 아니다.**
BE 관련 **7 suites/91 PASS**, FE **323 suites/3,164 PASS**, TypeScript/두 저장소 diff check PASS.
같은 독립 시뮬레이터에서 합성 관측 **16사례+서버 단절 1사례**를 확인했다. 최종 불변성
보강 뒤 정상/신규 5사례/원본 누락도 다시 확인했다. 후속 순환 구간 우회 수정 뒤 새 번들의
정상/순환 차단을 확인했다. 열차 관측을 승객 위치/탑승으로 표시하지
않으며 실제 공급자·GPS·APNs는 이 검사에서 0회다. native 변경/새 빌드는 없다.
[구현·자동 검사·독립 화면 증거 및 남은 연결 조건](journey-subway-catalog-validation-20261013.md).

## 혼합 경로 Activity API·영속 종료 연결 — 오프라인·독립 화면 검증

실제 APNs 승인 전 별도 test-source opt-in으로 5구간 안내→실제 Activity HTTP API/DB를
연결했다. 고정 합성 sender만 사용하며 Firebase/APNs 전송은 0회다. 전경 게시기는 명시적으로
시작하고 GPS 출발 ACK 뒤 신선한 현재 구간만 제한 전송한다. 단계 명령/실제 토큰 읽기는 없다.
FE **323 suites/3,159**, BE 관련 **3 suites/38 PASS**. 서버 파일 DB 재시작·취소/교체·
v4 수명·앱 END 없는 TTL 만료 정리·END 단발과 nested raw-field 거절을 검사했다.
독립 창 GPS replay는 exit 0이며 실제 상세의 다음 버스 위치/ETA와 로컬 잠금 Activity,
서버 UPDATE 14/END 1/STOPPED/END ACCEPTED를 확인했다. 잠금 뒤 Controls 메뉴의 조작 도구
오류로 최종 화면이 일시 보류됐지만 다음 턴 재조회에서 복구됐다. 동일 독립 창의 잠금 카드
제거→전경 DESTINATION_ARRIVED/STOPPED/자동 출발 1/native 종료 큐 0/게시기 END_ACCEPTED까지
확인했다. embedded Hub/실기기로 우회하지 않았다. 실제 APNs/지하철/전체 기능 완료는 아니다.
운영 재기동/배포/기본 ON, 실제 APNs 및 지하철 제품 연결은 완료로 바꾸지 않는다.
[구현·자동 검사·독립 화면 범위와 제어 오류 기록](journey-mixed-activity-offline-validation-20261013.md).

## 장시간 안내 수명 계약 v4 — 구현·독립 E2E 진행 중

신규 admission 5분은 유지하고, 인증된 영속 준비/정확한 별도 도보 snapshot v4에만
최대 2시간 안내 수명을 추가했다. GPS/차량 신선도·30초 서버 검증 lease·취소/교체/권한
fence는 연장하지 않는다. 두 신규 서버 opt-in은 기본 OFF이고 운영 설정/DDL 변경은 없다.
기존 v3의 10분 계약과 local/SANDBOX 상한은 그대로다. 상세 동의/잔여 시간/지도도 구분한다.
초기 FE 320 suites/3,097·Swift 366·BE 관련 32 suites/206·타입/iOS Debug build·replay 3 PASS.
첫 장시간 잠금 GPS는 600초 합성 인증 만료로 FAIL/자동 안전 종료였다. 실패 로그/화면을
보존하고 준비·명시적 복구 전에 인증이 고정 세션 만료+30초를 덮는지 FE/native가 검사하도록
보강했다. 부족하면 전경 갱신 후 재검사하며 백그라운드 인증 연장/refresh secret 저장은 없다.
후속 FE 320 suites/3,111·Swift 367·타입/iOS 빌드·BE 관련 17 PASS. 장시간 재시험은 약 12분
GPS replay/중간부터 연속 잠금→다음 버스 대기 1분→최종 도보 10m→자동 도착/카드 제거/
종료 대기 0 PASS다. 실제 2시간/잠금 중 인증 갱신/신규 APNs/현장 주행 증거는 아니다.

추가했다. 후속 FE **321 suites/3,129·타입 PASS**. 독립 창의 명시적 채널 선택·GPS 이동/
환승·잠금 두 번째 버스 하차 60m·자동 도착/Activity 제거/종료 대기 0을 확인했다.

## 환승 도보 handoff·표시 계약 (이전 부분 구현 기록)

후속으로 공식 정류장 목록 `getStaionByRoute`와 노선 형상 `getRoutePath`의 내부 어댑터·엄격 XML 계약을
추가하고 **31 suites / 259건** 합성 회귀를 통과했다. 정류장/형상의 `gpsX/gpsY`는 공식 WGS84 계약으로만
읽으며 `posX/posY`를 대체 좌표로 사용하지 않는다. 이 명세를 차량 위치 응답의 좌표계 인증으로 전용하지 않는다.
사용자는 두 메타데이터 API 각 1회, 합계 최대 2회 HTTP 시험을 승인했다. 버스 키 중복 두 항목이 동일한 값임을
확인해 단일 값만 일회 프로세스에 전달했다. 정류장 첫 조회는 **HTTP 401**로 거절돼 즉시 중단했고 형상은 미호출이다.
자동 재시도·다른 키 사용·운영 설정 변경은 없다. 정류장 재조회는 기존 각 1회 승인을 재사용하지 않는다.
`SEOUL_SUBWAY_API_KEY`는 존재 여부만 확인했다. 키 원문을 출력하거나 `.env`를 수정하지 않았다.
현재 키의 노선정보조회 서비스 접근/승인 상태를 확인해야 하며, 401만으로 키 오류나 제공처 원인을 단정하지 않는다.
401 즉시 중단·두 번째 조회 차단·오류 원문 비노출 회귀를 추가해 **31 suites / 260건**을 재통과했다.
R2에는 별도 차량 동행 코어의 첫 slice를 추가하고 새 15건/전체 Swift 285건을 통과했다.
기존 설치 앱의 독립 창에서 7016 안내 차단·정상 상세 표시를 재확인했으나 새 코어가 연결된 E2E가 아니다.
[R2 코어 검증과 E2E 경계](journey-r2-bus-ride-core-validation-20261007.md).
R2 전체/R3–R6 및 새 기능 독립 시뮬레이터 E2E는 아직 미완료다.

사용자가 공식 API 사용 신청과 키 추가를 완료했다. HTTPS는 이 실행 환경에서 시간 초과됐으며,
평문 위험 설명 후 승인된 최초 HTTP 1회는 3행 모두 만료였고, **별도 승인된 1분·최대 6회 표본**은
5회에서 신선 관측을 확보했다. 반복 관측 12행 중 9행 수용/3행 만료, 나이는 7.281~22.199초다.
source TTL 15초는 그대로 유지했으며 마지막 표본은 전부 만료로 거부했다. 집계만으로 차량별 고정 갱신 주기를 인증하지 않는다.
승인된 두 시험은 종료됐고 자동 재시도/HTTP 전환/운영 설정 변경은 없다. 다음은 좌표계·도로 구간/정류장·방면 매핑과
도보 geometry·quota/polling 예산이다. 현재 결과를 차량 동행·자동 탑승/하차·경로 바 연동 합격으로 간주하지 않는다.

실제 노선 시험 대상: **서울 7016 상명대 방면, 서울역→경복궁역**. 공식 정류장/형상/차량 위치 자료를 조회하고 독립 시뮬레이터의 미지원 경로 차단·상세 표시 E2E를 수행했다. 상세 label 누락 crash와 미확인 시간의 가짜 표시를 수정했다. 실제 자동 탑승·하차/완주 성공은 아니며, 도보 geometry·공식 adapter·차량 동행 증거 연결이 다음 선행 작업이다. [7016 시험 결과와 후속 순서](journey-seoul-7016-validation-20261007.md).

문서 상태: 2026-10-07 P2-3d3d에서 BE main-source에 암호화된 Activity 소유권/FCM 소유권 fence와 durable END 예약·dispatcher를 추가했다. 독립 시뮬레이터에서 GPS ACTIVE→앱 terminate→서버 process restart→DB 세션 만료 복구→실제 APNs END 수락·잠금 카드 제거→두 번째 서버 restart 전송 0→cold 자동 정리·새 준비/종료를 통과했다. 실제 MySQL 8.4의 migration/Hibernate validate/재시작·동시 claim은 별도 합성 provider 통합 검사로 통과했다. 운영 DB/서버에는 적용하지 않았다. token 회전·새 로그인 세대/실제 인증·오프라인 stale·전체 접근성·장시간 안내 수명/실제 공급자·버스 완주/P3/P4는 미완료다. 현재 첫 도보·승차 정류장 접근/대기 지원이며 P2 전체 완료가 아니다. 시험 opt-in ON, 운영 default-off 유지. [최신 증거](journey-durable-end-validation-20261007.md).
작업 브랜치: FE·BE 각각 `feature/transit-guidance-v1`.
우선 플랫폼: iOS. Android는 동일 계약과 검증 시나리오를 재사용하는 후속 단계다.

## 1 목표와 확정 요구사항

목표는 사용자가 실제로 이동하면 앱이 출발·탑승·하차·환승·도착을 판단하고,
현재 위치와 다음 행동을 안내하는 대중교통 내비게이션이다. 수동 체크리스트가 아니다.

- 출발 버튼으로 출발 여부를 판단하지 않는다. 동의한 자동 안내 세션에서 실제 이동으로 감지한다.
- 탑승·하차·환승·다음 단계 버튼을 제품에서 제거한다. 불확실할 때도 수동 보정 버튼으로 대체하지 않는다.
- 앱 지도에 현재 위치, 선택 경로, 현재 구간과 목적지까지의 진행 상황을 표시한다.
- 전체 경로를 원본 순서의 도보·버스·지하철·환승 구간으로 나눈 색상 바에 표시한다. **바 위의 내 위치 마커는 현재 구간 안에서 이동**한다. 단순 완료 구간 비율이나 첫 도보 퍼센트 카드가 최종 화면이 아니다.
- 상세 지도 위치 점, 전체 경로 바 위치 마커, 상세 목록의 현재 구간·정류장은 동일한 엔진 관측에서 파생한다. Live Activity에도 같은 전체 경로와 마커를 표시한다.
- 검증된 실시간 정보로 “○○행 열차가 약 2분 뒤 도착합니다”를 안내한다.
- 예정 하차 지점 한 정류장 전과 해당 정류장 접근 시 하차를 안내한다.
- 환승 노선·방면과 대기시간을 안내하고, 승강장·출구 정보는 근거가 있을 때만 제공한다.
- 화면이 잠겨도 안내가 이어지고, Live Activity와 Dynamic Island에 현재 구간·다음 행동을 표시한다.
- Live Activity는 큰 단계/지점명, 잔여 도보 거리, 둥근 색상 경로 바와 현재 위치 화살표를 중심으로 구성한다. 사용자 문구에 진행률 퍼센트를 노출하지 않는다. “구로역까지 · 도보 약 100m”, “구로역 · 버스 대기”처럼 검증된 데이터만 사용한다. “다음 정류장에서 탑승/하차”는 정류장 순서·현재 차량/탑승 근거가 확보된 후 표시한다.
- 음성 안내와 알림을 조율한다. 기기 무음 모드에서는 음성 대신 알림을 제공하는 경험이 요구사항이다.
- GPS·교통정보가 불확실하면 “위치 확인 중”, “정보 지연”으로 표시하고 정밀한 안내를 만들어내지 않는다.
- 경로 이탈, 잘못된 탑승, 하차 지점 지나침을 감지하고 재탐색·복구하는 단계까지 계획에 포함한다.

안내 활성화·종료·음성 설정은 사용자 제어로 남길 수 있다. 이는 이동 단계를 사용자가 확인하는
버튼과 다르다. 자동 감지는 동의한 일정과 제한된 시간 범위에서만 작동하며 상시 위치 추적을 뜻하지 않는다.

네이버 지도와 유사한 사용 경험을 목표로 하되, 동일한 데이터 접근성·전국 지원·정확도를
현재 확보했다고 가정하지 않는다. 지원 지역과 노선은 제공처 데이터와 현장 검증 결과로 확정한다.

## 2 별도 엔진의 범위

이번에 만드는 것은 기존 경로 검색 위에서 동작하는 `NoLate Journey Engine`이다.

| 구성 | 역할 | 개발 방향 |
| --- | --- | --- |
| 경로 검색과 재탐색 | 목적지까지의 대중교통 경로 후보 생성 | 기존 공급자 연동 재사용, RoutePlanner 인터페이스로 분리 |
| 자동 진행 엔진 | 실제 위치와 교통정보로 현재 구간·탑승·하차·환승 판단 | 독립 모듈로 신규 개발 |
| 안내 채널 | 지도, 음성, 알림, Live Activity에 같은 판단 반영 | 공통 상태와 이벤트를 소비하도록 통합 |

전국 교통망·시간표를 수집해 자체 최단경로 알고리즘까지 만드는 프로젝트는 이번 범위가 아니다.
반면 자동 진행 엔진은 화면이나 특정 지도 SDK에 종속시키지 않는다. 향후 경로 공급자가 바뀌어도
정규화 어댑터만 교체할 수 있게 한다.

## 4 권장 엔진 구조

iOS는 Swift 기반 순수 판정 코어와 네이티브 Runtime으로 시작한다. React Native는 지도·설정·상태
표시를 담당하며 JS 타이머나 화면 마운트 여부가 안내 실행을 좌우하지 않게 한다.
Android에서는 계약·정책·replay fixture를 공유하고 실행부를 별도 구현한다.
Swift 코드를 그대로 Android에서 재사용할 수 있다고 전제하지 않는다.

~~~text
원본 경로 → RouteNormalizer ─────────────────┐
기기 위치 → LocationAdapter → RouteMatcher ─┼→ JourneyEngineCore
실시간 정보 → TransitObservationAdapter ────┘       │
                                                   ├→ JourneySnapshot → 지도와 진행 화면
                                                   └→ GuidanceEvent
                                                         ├→ 음성
                                                         ├→ 로컬 안내 알림
                                                         └→ Live Activity projection
                                                                  ↕
                                                     서버 동기화와 실제 APNs
~~~

| 모듈 | 책임 |
| --- | --- |
| JourneyEngineCore | 입력 관측·시간·정책으로 상태와 이벤트를 결정하는 순수 로직 |
| JourneyRuntime | 위치 세션, 직렬 실행, 저장·복구, 권한, 배터리 정책, 네이티브 채널 수명 관리 |
| RouteNormalizer | 원본 leg·정류장 순서·방면·geometry 출처와 품질을 표준 계약으로 변환 |
| RouteMatcher | 경로상 거리, 정류장 순번, 방향, 이탈 후보와 신뢰도 계산 |
| TransitObservationAdapter | 도착 예상과 차량 위치를 구분하고 제공처 ID·최신성·지원 능력을 정규화 |
| GuidanceEventRouter | 우선순위, 유효기간, 중복 방지, 음성·알림 채널 선택 |
| JourneySync | 세션 소유권, 관측 업로드, 오프라인 큐, 경로 버전, 재접속 조정 |
| RoutePlanner | 기존 경로 검색으로 재탐색 후 새 경로 버전 준비 |

서버는 교통정보 중계·캐시·quota 보호·세션 검증·APNs 전송을 담당한다.
기기에서 판단 가능한 하차 음성·로컬 알림은 서버 왕복을 기다리지 않는다.
원시 위치는 기본적으로 기기에서 처리하고 서버에는 필요한 최소 파생 상태만 보낸다.

## 5 상태와 데이터 계약

### 5.1 세션과 이동 상태 분리

- 세션 생명주기: `ARMED → ACTIVE → ARRIVED / STOPPED / EXPIRED`.
- ACTIVE 이동 단계: `WALKING_TO_STOP → WAITING → RIDING → TRANSFERRING / FINAL_WALK`.
- 품질 상태: `RELIABLE / UNCERTAIN / STALE / UNAVAILABLE`. 이동 단계와 별도 축이다.
- 경로 상태: `ON_ROUTE / OFF_ROUTE_CANDIDATE / REROUTING`. 한 번의 GPS 튐으로 재탐색하지 않는다.

`ARMED`는 자동 출발 감지를 준비한 상태다. 아직 일정의 출발 완료 처리나 출발 알람 취소를 하지 않는다.
실제 이동을 충분히 관측해 ACTIVE가 될 때 기존 출발 처리와 연결한다.
현재 start API는 바로 출발 처리하므로, 준비용으로 그대로 호출하면 안 된다.

오프라인에서 출발을 판정하면 기기의 기존 출발 알람을 정리하고 서버 활성화 요청을 영속 보관한다.
재접속 시 멱등하게 반영하며, 동기화 전 서버 출발 알림이 도착할 수 있는 경쟁 조건을 별도로 다룬다.
네트워크가 끊긴 상태에서 원격 알림까지 즉시 취소된다고 보장하지 않는다.

“다음 정류장에서 하차”는 안내 이벤트이지 하차 완료의 증거가 아니다.
하차 지점 접근만으로 RIDING을 끝내지 않는다. 이동 패턴·경로 분리 등의 후속 증거로 판단한다.
GPS 단절도 하차·환승·도착의 증거로 사용하지 않는다.

여정 하나의 진행 판정 소유자는 하나의 기기·Runtime이다. 다른 기기는 읽기 전용으로 두고,
기기 교체 시 명시적 소유권 이전과 generation 변경이 필요하다. 새 일정 안내·로그아웃·종료 시
기존 위치 세션과 안내 큐를 정리한다. 단절 중 소유권 처리는 TTL 정책과 복구 테스트로 검증한다.

### 5.3 화면 위치 계약 (사용자 예시 반영)

- 경로의 정적인 구간 순서는 검증된 원본 경로에서 가져온다. 진행 상태와 분리하여 위치가 불확실해도 전체 경로는 남긴다.
- 위치 표시는 `현재 구간 + 구간 내 경로상 진행 비율 + 관측 유효기간`으로 표현한다. 바 좌표는 표시용이며 지리 좌표/남은 시간을 뜻하지 않는다.
- P2-3c 첫 연결은 모든 구간을 동일 폭으로 표시한다. 시간·거리 비례 폭과 검증된 노선명·노선색은 별도 표시 메타데이터 단계에서 추가하며 임의 값을 만들지 않는다.
- 승차 정류장 대기는 첫 도보 끝/다음 교통 구간 시작의 경계에 표시한다. 대기 상태를 버스 탑승이나 버스 구간 100%로 표현하지 않는다.
- stale·탑승 후보·경로 불일치에서는 정밀 위치 마커를 숨기고 확인 필요를 표시한다. 타이머는 정보 만료만 처리하며 마커를 앞으로 이동시키지 않는다.
- 원시 GPS는 상세 지도의 임시 위치 표시로 제한한다. Activity/APNs에는 파생 진행 위치만 사용한다.

`eventKey`는 세션·세대·경로 버전·구간·사건·대상 조합으로 만든다. 도착 예정 차량이 바뀌면
새로운 대기 안내 대상일 수 있으므로 시간 버킷만으로 식별하지 않는다.
처리 기록과 sequence를 저장해 재시작·재전송에서 중복을 억제한다.
OS 알림까지 절대적인 exactly-once 전달을 보장한다고 표현하지 않는다.

## 6 자동 판정과 교통정보

### 6.1 모드별 판정

- 자동 출발: 출발지 주변 단순 GPS 흔들림이 아니라 지속 이동·거리·방향·예정 경로의 증거를 결합한다.
- 도보: 검증된 형상에 위치를 투영해 경로상 진행 거리를 계산한다.
- 탑승: 승차 지점 접근·대기 이력, 속도 변화, 연속 경로 일치, 노선 방향과 가능한 차량 정보를 결합한다.
- 버스 이동: 정류장 순서와 경로상 진행을 추적한다. 가장 가까운 정류장만 고르면 왕복·순환·평행 노선에서 오판한다.
- 지하철: 역·방면·진입 이력·실시간 열차 정보·이동 시간을 결합하되, 터널에서 시간 경과만으로 현재 역을 확정하지 않는다.
- 하차와 환승: 하차 지점·도보 전환·차량 경로 이탈·다음 승차 지점 접근을 함께 판단한다.
- 도착: 최종 구간, 목적지 접근과 체류를 확인한다. 목적지 인근 도로를 지나간 것만으로 종료하지 않는다.

같은 도로의 다른 버스나 반대 방향 차량을 구분할 근거가 부족하면 탑승을 단정하지 않는다.
이때 정밀 안내를 억제한 횟수도 품질 지표에 포함한다. 계속 “확인 중”만 표시하는 엔진을
오탐이 없다는 이유로 출시하지 않는다.

정확도·거리·속도·체류 시간·hysteresis·임계값은 하나의 버전 관리 정책으로 모은다.
stale/out-of-order 관측과 비정상 점프를 필터링하고, 합성 및 동의받은 현장 trace로 조정한다.

### 6.2 도착정보와 차량 추적은 다른 데이터다

현재 TAGO의 `remainingStops`는 도착 예정 버스가 조회한 승차 정류장까지 오는 데 남은
정류장 수다. 사용자가 탄 버스에서 목적 하차 정류장까지 남은 수로 사용하면 안 된다.

신규 엔진에서는 `incomingVehicleStopsAway`와 `riderStopsToAlight`를 분리한다.
기존 DTO는 소비자를 확인한 뒤 호환성 있게 변경한다.
현재 도착 DTO만으로 안정적인 차량 식별·차량 GPS·현재 정류장 순번을 얻는다고 가정하지 않는다.

P0에서 제공처·지역·노선별로 다음 지원 능력 표를 작성한다.

- 경로 형상과 정류장 전체 순서·좌표의 유무와 품질.
- route/stop/vehicle/train ID, 방면·종착역과 실제 매칭 가능성.
- 차량 위치·정류장 통과 정보 제공 여부.
- 원본 갱신 시각, TTL, 갱신 주기, 데이터 사용 범위와 호출 한도.
- 데이터 미제공·장애·빈 결과를 구분할 수 있는지.

권장 첫 검증 지역은 기존 연동이 있는 서울이다. 지원 노선은 실데이터 확인 후 정한다.
필수 정보가 없는 지역을 전국 동일 수준 지원으로 묶지 않는다. 새로운 유료 계약·데이터 구매가
필요하면 비용과 범위를 제시하고 별도 결정한다.

### 6.3 실시간 대기 안내

현재/다음 승차 구간만 상황에 맞춰 조회한다. 서버 공유 캐시·요청 병합·quota 보호를 적용한다.
“2분 남음”은 해당 방면·차량의 신선한 ETA에 근거한 임계 구간 진입 이벤트다.
2분과 3분 사이 변동마다 반복하지 않으며, ETA가 지연되거나 차량이 바뀌면 정책에 따라 갱신한다.

수신 시각이 최신인 것과 원본 정보가 최신인 것을 구분한다.
`LOCAL_RECEIPT_TIMESTAMP_ONLY` 또는 만료 데이터로 “곧 도착”, “지금 타세요”를 발화하지 않는다.
무응답·오래된 데이터는 정보 지연으로 표시하고 타이머만으로 최신 도착정보를 만들어내지 않는다.

## 7 음성 알림과 잠금 상태

### 7.1 공통 안내 정책

| 사건 | 음성 사용 가능 시 | 무음 또는 음성 사용 불가 시 | 화면과 Live Activity |
| --- | --- | --- | --- |
| 자동 출발 | 안내 시작 | 기본적으로 과도한 알림 생략 | 이동 중으로 전환 |
| 열차·버스 약 2분 전 | 검증된 대기시간 안내 | 대기 안내 알림 | 노선·방면·대기시간 |
| 하차 한 정류장 전 | 하차 준비 안내 | 하차 준비 알림 | 다음 정류장과 하차 지점 |
| 하차 지점 접근 | 해당 지점 하차 안내 | 높은 우선순위 알림 | 하차 지점 강조 |
| 환승 | 다음 노선·방면 안내 | 환승 안내 알림 | 다음 행동·대기시간 |
| 경로 이탈과 변경 | 확인된 이탈·새 경로 안내 | 경로 변경 알림 | 재탐색 상태·새 경로 |
| 목적지 도착 | 도착 안내 | 필요 시 도착 알림 | 도착 후 종료 |

iOS 음성은 AVSpeechSynthesizer를 사용하며 기존 반복 알람과 오디오 세션 사용을 조율한다.
하차·환승 안내가 일반 대기 안내보다 우선한다. 종료·재탐색 시 과거 음성 큐를 폐기한다.
음성 끄기는 TTS만 중단하고 위치 추적·Live Activity·알림은 유지한다.
안내 종료는 위치·TTS·조회·예약 알림·Live Activity를 모두 정리한다.

기기에서 즉시 판단한 하차 사건은 로컬 알림을 우선 사용한다. 서버 정보 사건에는 원격 푸시를
사용할 수 있으나, 같은 사건을 로컬과 원격에서 독립적으로 중복 발송하지 않도록 소유권을 정한다.
발송 전 세션·경로·유효기간을 검사하고 이미 지난 사건은 발송하지 않는다.
이미 OS에 전달된 원격 알림을 항상 회수할 수 있다고 가정하지 않는다.

집중 모드·알림 권한·알림 요약 등 OS 설정이 표시를 제한할 수 있다.
긴급 중요 알림 권한을 가정하거나 무음 설정을 우회하지 않는다.

### 7.2 무음 모드 요구사항은 사전 기술 검증 대상

잠금 중 재생과 기기 무음 스위치 준수는 같은 설정 하나로 해결된다고 단정할 수 없다.
Apple의 playback 카테고리는 잠금 중 재생을 지원하지만 무음 스위치에서도 재생한다.
기본/ambient 계열은 무음뿐 아니라 화면 잠금에도 영향을 받는다.
[Apple playback](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/playback),
[Apple 오디오 카테고리](https://developer.apple.com/library/archive/documentation/Audio/Conceptual/AudioSessionProgrammingGuide/AudioSessionCategoriesandModes/AudioSessionCategoriesandModes.html).

지원 iOS·기기에서 무음 전환, 잠금, 이어폰, 음악, 통화 중 조합을 실제 검증한다.
`isOutputMuted`는 오디오 세션 출력 상태 API이며 기기 무음 스위치 감지의 증거로 간주하지 않는다.
[Apple isOutputMuted](https://developer.apple.com/documentation/avfaudio/avaudiosession/isoutputmuted).

“기기 무음이면 자동으로 알림 전환”을 지원 범위에서 충족할 수 없으면 P0 결과를 보고하고
지원 OS 제한 또는 사용자가 선택하는 안내 모드 등 대안을 협의한다.
앱 내 음소거 버튼만 구현하고 원래 요구사항을 완료 처리하지 않는다.

## 8 Live Activity와 APNs 일관성

지도는 앱 안에 표시한다. Live Activity는 현재 구간, 남은 정류장 또는 거리,
다음 행동, 검증된 대기시간을 간결하게 보여준다. 알 수 없는 수치는 숨기며
마지막 신뢰 가능한 관측 시각과 stale 상태를 구분한다.

권장안은 활성 여정의 네이티브 엔진이 하나의 논리적 상태 발행자가 되고,
로컬 ActivityKit과 서버 APNs가 같은 확정 스냅샷을 전달하는 구조다.
서버가 별도 추정으로 구간을 앞당기거나 과거 진행을 최신 값으로 다시 발행하지 않는다.

- 세션 시작·출발 전 서버 발행에서 활성 엔진 발행으로 넘기는 소유권 절차를 정의한다.
- publicationTimestamp와 revision을 스냅샷 생성 시 정하고 재시도 시 현재 시각으로 바꾸지 않는다.
- 서버는 최신 유효 스냅샷만 전송한다. 종료·경로 변경·세대 변경 뒤 과거 payload를 폐기한다.
- 로컬 update와 APNs 모두 순서 비교 가능한 timestamp를 사용한다.
- APNs 초 단위 timestamp의 동률, 기기·서버 시계 차이, 재시작, 오프라인 복귀를 P0에서 시험한다.
- 같은 발행 시각에 서로 다른 내용이 생기지 않도록 병합·발행 정책을 정한다.
- GPS 샘플마다 발행하지 않고 정류장·구간·안내 변경 등 의미 있는 변화를 반영한다.

서버의 새 ETA도 기기 엔진의 입력으로 반영한 뒤 스냅샷을 발행한다.
발행 시각과 내용 해시를 함께 보존하고, Live Activity 표현만 같은 초의 변경을 병합한다.
음성·로컬 알림·앱 화면은 이 병합을 기다리지 않는다. 시계 변경은 세션 기준 시각과
단조 증가 시간, 마지막 발행값 복원으로 다루며 임의의 미래 시각으로 순서를 강제하지 않는다.
이전 generation의 종료 이벤트를 새 Activity 토큰으로 보내지 않는다.

Apple은 timestamp가 이전 update/push보다 오래된 로컬 업데이트를 무시한다고 설명한다.
커스텀 revision 필드만으로 OS가 직접 적용하는 APNs 덮어쓰기를 막을 수 있다고 가정하지 않는다.
[Apple timestamp 기반 업데이트](https://developer.apple.com/documentation/activitykit/activity/update%28_%3Aalertconfiguration%3Atimestamp%3A%29).

현재 앱의 최소 iOS는 16.6이지만 위 timestamp 지정 API는 SDK 기준 iOS 17.2 이상이다.
자동 안내 기능의 지원 버전과 16.6~17.1의 단일 전송 정책은 P0에서 결정한다.
전체 앱의 최소 버전을 임의로 올리거나 구버전에서도 동일한 이중 전송이 된다고 가정하지 않는다.

위 정합성이 검증되지 않으면 단일 발행 경로로 기술 파일럿을 제한한다.
서버 전용 경로는 오프라인에서 Live Activity 진행이 지연되는 제약을 명시하며,
이를 최종 자동 안내 요구사항 충족으로 간주하지 않는다. 음성·로컬 안내는 서버 연결과 분리한다.

실제 전송 검증은 기존 서버 → FCM → APNs → ActivityKit 경로를 포함한다.
직접 APNs 전송은 구간 진단용이며, 기존 서비스 경로의 성공을 대체하지 않는다.
push-to-start·활동별 update 토큰·토큰 교체·종료를 구분한다.

Apple은 조건을 갖춘 Simulator에서도 실제 ActivityKit APNs 테스트를 지원한다.
따라서 시뮬레이터라고 무조건 불가능하다고 단정하지 않되,
preview·로컬 생성·simctl payload 주입은 실제 APNs 전달 증거로 인정하지 않는다.
[Apple ActivityKit push 검증](https://developer.apple.com/documentation/ActivityKit/starting-and-updating-live-activities-with-activitykit-push-notifications).

## 9 백그라운드 복구와 재탐색

사용자에게 이유를 설명하고 필요한 위치·알림 권한을 요청한다.
When In Use와 활성 백그라운드 위치 세션으로 가능한 범위를 먼저 검증하고,
자동 대기 감지 등 Always가 필요한 경우에만 별도 근거와 동의 흐름을 마련한다.
선택할 Core Location API는 최소 지원 OS와 맞춰 확정한다.
[Apple 백그라운드 위치 처리](https://developer.apple.com/documentation/corelocation/handling-location-updates-in-the-background).

권한이 없으면 불가능한 자동 안내를 켜진 것처럼 표시하지 않는다. 전경에서만 가능한 경우
그 범위를 알리고, 수동 단계 진행 모드로 대체하지 않는다. 안내 대기 시간과 세션 만료를 제한한다.

앱 화면 재진입, JS 재시작, OS 종료 후 재실행, 사용자의 강제 종료를 서로 다른 시나리오로 검증한다.
마지막 상태만 저장해 두었다고 안내가 계속 실행된 것은 아니다. 복구 시 관측 최신성과
서버 소유권을 재검사하고 과거 음성·알림을 재생하지 않는다.
강제 종료 후 지속 추적을 보장하지 않으며 APNs가 누락된 위치 관측을 대신한다고 설명하지 않는다.

이탈이 확인되면 새 경로를 준비한 뒤 routeRevision을 원자적으로 교체한다.
이전 경로의 음성 큐·예약 알림·조회·전송 대기를 함께 무효화한다.
버스를 탄 채 하차 지점을 지난 경우 즉시 걸어서 되돌아가라고 하지 않고 현재 이동 수단을 고려한다.
재탐색 실패 시 기존 경로를 최신 경로인 것처럼 안내하지 않고 복구 중임을 표시한다.

## 10 구현 순서와 단계별 통과 기준

### P0 데이터와 iOS 핵심 제약 검증

모바일과 백엔드가 병렬로 진행한다.

현재 실행 범위는 사용자 결정에 따라 **시뮬레이터만**이다. 연결된 실기기를 사용하지 않는다.
아래 실기기·현장 통과 기준은 삭제하거나 시뮬레이터 결과로 대체하지 않고 후속 검증으로 남긴다.
개발 전용 네이티브 위치·음성 진단과 교통정보 계약 테스트를 추가했다.
세부 증거와 미검증 항목은 [P0 검증 기록](journey-engine-p0-validation.md)에 누적한다.

- 모바일: 실제 기기 잠금 중 위치·TTS·무음 전환 검증, 네이티브 실행 수명 실험.
- 백엔드: 후보 버스·지하철의 제공처 필드와 최신성, 차량 식별·정류장 매핑 확인.
- 공통: 실제 FCM/APNs 시작·갱신·종료와 로컬/원격 순서 경쟁 검증.
- 산출물: 지원 능력 표, 지원 OS·기기 행렬, 증거 로그·스크린샷, 데이터 부족 목록.

통과 기준: 첫 버스 경로에 필요한 관측을 확보하고 지원 가능한 안내 수준을 설명할 수 있음.
무음 요구사항과 ActivityKit 발행 정책의 가능/불가가 명확함.
부족한 데이터나 OS 제약을 수동 버튼으로 우회하지 않음.

### P1 화면 독립 엔진과 기록 재생 기반

- 계약·ARMED/ACTIVE·판정 소유권과 정책 버전 확정.
- Swift Core, Runtime, RouteNormalizer, replay harness 구축.
- 지속 위치 수집·저장·복구와 RN 상태 구독 연결.
- 자동 관측 API, 멱등적인 출발 활성화, 오프라인 동기화 추가.
- 순환·왕복 경로, GPS jump, 단절, 오래된·역순 관측 fixture 작성.

통과 기준: 같은 입력과 정책에서 같은 상태·사건이 재현됨.
화면을 닫아도 Runtime이 화면 수명 때문에 종료되지 않음.
GPS 흔들림만으로 출발·하차·도착하지 않고 수동 진행 이벤트에 의존하지 않음.

#### P1-1 자동 출발 첫 slice 진행 상태

고정 공개 좌표의 합성 경로에서 `ARMED → ACTIVE`만 판정하는 Foundation Swift Core와
개발용 네이티브 Runtime·RN 구독 화면을 구현했다. Runtime은 Debug 시뮬레이터 및 진단
opt-in으로 제한하고, 실제 일정 출발 처리·알람 취소·서버 API·Live Activity에는 연결하지 않는다.
준비·기록 재생·복구·종료는 시험 제어이며 출발·탑승·하차를 수동 확정하는 버튼이 아니다.

Core 39개·checkpoint 18개를 포함한 Swift package 87개, 신규 FE 21개를 포함한 전체 FE
1,939개 테스트가 통과했다. Debug iOS 통합 빌드와 지정된 P0 독립 창에서 정지·이동 감지,
화면 이탈, 잠금 중 위치 처리, 재실행·명시 복구, 중지 후 추가 입력 무시를 확인했다.
10분 전체 만료·권한 철회·실제 APNs는 이번 E2E 통과 항목이 아니다.
상세 관측과 증거는 [P1 부분 구현 검증](journey-engine-p1-validation.md)에 기록한다.

위치 신뢰도가 끊겨 이동 증거가 초기화된 뒤 출발지 35m 밖이라면 현재 코어는 출발을
추측하지 않고 보류한다. 실제 경로의 재획득·탑승·하차·환승·음성·원격 APNs는 후속 단계다.
이 부분 진행은 P0 전체 게이트 통과나 P1 전체 완료를 의미하지 않는다.

#### P1-2 경로 정규화·품질 계약 진행 상태

TMAP/ODsay 파서에서 표시용 값과 분리한 원본 정류장 순서·방면·형상 보존 근거를 추가했다.
기존 경로 객체 → 제한된 입력 계약 → Foundation Swift RouteNormalizer → 품질 요약 연결을 구현했다.
정류장 직선, 원본 순번 누락, 역방향·오류 좌표, 샘플링으로 손실된 형상, 출처가 없는 저장 경로를
실주행 가능한 경로로 승격하지 않는다. 검사는 읽기 전용이며 실제 선택 경로의 Runtime arm/시작은 아직 연결하지 않는다.

Swift package 136개, FE 전체 269 suites / 2,155개, 타입 검사·소유 파일 lint·진단 설정 7개 및
iOS 통합 빌드가 통과했다. 같은 P0 독립 창에서 실제 파서를 거치는 합성 입력 여섯 종류와
검사 후 위치 미수집을 확인했다. 실제 공급자 응답·실주행·APNs 검증을 대신하지 않는다.
정책 한계와 스크린샷은 [P1-2 검증 기록](journey-engine-p1-2-validation.md)에 기록한다.

#### P1-3 선택 경로 준비·자동 출발 동기화 진행 상태

새 선택 경로에서 품질 검사·동의 후 네이티브 자동 감지를 준비하는 개발용 진입점을 추가했다.
준비는 ARMED이며 출발 버튼이나 단계 전환 버튼은 없다. 일정 저장/수동 start API와 분리했다.
실제 선택 경로 진입은 LOCAL_ONLY, 합성 시험 화면은 고정 loopback SANDBOX로 제한한다.
기기 내 atomic envelope에 출발 사건을 보관하고, 서버의 별도 준비/멱등 출발 API와 연결했다.
화면 종료·로그아웃·중복 응답·명시 복구·저장 실패를 각각 처리하고 운영 기능은 기본 OFF다.

세부 테스트 수치, 독립 창 화면 검증, 발견 후 수정한 계약 불일치와 한계는
[P1-3 검증 기록](journey-engine-p1-3-validation.md)에 기록한다.
이 단계는 실제 일정 운영 연결, 오프라인 로컬 출발 알람 정리, 지속 이동 상태 업로드,
Live Activity 갱신까지 완료했다는 뜻이 아니다. 전송 펌프의 배경 JS 중단도 후속 과제다.

다음은 지원 버스의 정류장 접근·대기·탑승 판정과 위 운영 연결 경계를 좁힌다.
실제 버스·열차 식별 및 최신성 데이터가 확보되기 전에는 구조 검사 통과를
자동 탑승·한 정류장 전 안내 가능 판정으로 사용하지 않는다.

### P2 버스 한 경로 자동 안내 완주

완성할 첫 수직 기능은 다음 흐름 전체다.

~~~text
안내 준비 → 실제 이동으로 출발 감지 → 정류장 접근과 대기
→ 자동 탑승 판단 → 한 정류장 전 안내 → 하차 지점 안내
→ 실제 하차 판단 → 최종 도보 → 자동 도착
~~~

이 단계부터 지도·TTS·알림·Live Activity를 모두 연결한다.
사용자용 탑승·하차·다음 단계 버튼을 제거한다.
앱 잠금, 동일 도로 다른 버스, 하차 지나침, 일시적 GPS·네트워크 단절도 시험한다.

통과 기준: 단계 확인 버튼 없이 실제 버스 탑승 경로를 완주하고,
하차 안내 시점·잠금 화면 상태를 기록으로 확인함.
좌표 replay 성공만으로 통과 처리하지 않음.

#### P2-1 첫 버스 접근·대기·탑승 후보 구현 체크포인트

첫 도보 바로 다음 BUS 구간에 별도 Swift 위치 관측 코어를 연결했다. 자동 출발 후 정류장 접근,
체류 대기, 경로상 지속 이동을 관측하며 `BOARDING_CANDIDATE`까지 표시한다. GPS만으로 특정 버스
탑승을 확정하지 않으므로 `boardingConfirmed=false`이고 RIDING·하차·안내 발화로 전환하지 않는다.
복구는 대기/탑승 후보 근거를 초기화하고 새 위치를 요구한다. 첫 도보 품질과 버스 품질은 분리한다.

개발용 실제 선택 경로는 LOCAL_ONLY를 유지하고, `/internal/journey-bus`는 합성 입력·격리 HTTP
SANDBOX를 사용한다. 운영 비활성·Debug 시뮬레이터 한정이며 출발·탑승·다음 단계 버튼은 없다.
BE에는 원천 시각·대기 관측 의미를 보존하는 순수 어댑터를 추가했지만 공급자/Runtime wiring,
노선·차량 ID 확보와 실제 사용자 일정 연결은 아직 하지 않았다.

FE 전체 275 suites / 2,324개, TypeScript·소유 파일 lint, replay 5개·진단 설정 7개,
BE 신규 어댑터 21개 + P0/기존 회귀 38개 = 59개, Swift 227개·strict typecheck가 통과했다.
지정 독립 창의 `simctl location` → CoreLocation → 접근·대기·후보 판정과 도보 통과·이탈·복구 E2E도 통과했다.
정확한 정책값·실행 결과·수정 전 실패와 검증 한계는 [P2-1 검증 기록](journey-engine-p2-1-validation.md)을 따른다.

다음 P2-2는 지원 공급자의 최신 도착 관측 연결과 선택 노선·방면·정류장·차량 식별 근거를 확보하는 단계다.
근거가 없는 공급자/노선은 계속 탑승 미확정으로 남긴다. 이후 확정 승하차·남은 정류장과 안내 채널을 연결한다.

실제 버스 탑승 확정, 한 정류장 전/하차 안내, 음성·푸시·Live Activity/APNs·현장 정확도는 미검증이다.
이 체크포인트는 P2의 시작 부분이며 위 버스 한 경로 완주 통과 기준을 충족했다는 뜻이 아니다.

#### P2-2a 도착 관측 연결 체크포인트 (이번 구현)

원천 시각을 검증하는 P2-1 어댑터에 요청 식별자 매처, 소유 세션을 검사하는 읽기 전용 API,
GPS 접근/대기 상태에서만 동작하는 개발용 도착 관측 카드를 연결했다. 서울 노선 ID와 도착 예정
차량 ID, TAGO 노선 ID를 원문 namespace에 보존한다. 도착 예정 차량은 사용자 탑승 차량이 아니다.

합성 sidecar의 정류장·노선·방면과 현재 session/generation/revision/digest를 대조한다.
다른 노선·반대 방면·오래된 원천 정보·위치 불확실·탑승 후보·종료에서는 대기시간을 숨긴다.
원래 합성 경로에는 실제 공급자 ID를 만들어 넣지 않았고, 실제 선택 경로는 LOCAL_ONLY로 남는다.
화면의 P2-2 표기는 이 체크포인트의 시험 화면이며 P2-2 전체 완료 표기가 아니다.

FE 전체 277 suites / 2,360개, BE 관련 회귀 93개, TypeScript·소유 파일 lint,
위치 replay/진단 설정 13개가 통과했다. 독립 창의 GPS → 자동 출발 → 대기 → 도착 관측과
불일치·stale·탑승 후보·종료 차단을 E2E로 확인했다.
정확한 범위·증거·수정 전 실패는 [P2-2 검증 기록](journey-engine-p2-2-validation.md)을 따른다.

#### 실제 경로 상세와 Live Activity 적용 순서

P2-2b에서는 저장 경로의 canonical query/승차 occurrence를 서버가 결정하고 선택 메타데이터와
대조하는 읽기 전용 binding API를 구현했다. ODsay busID와 지역 BIS route ID를 구별하고,
raw ID·서울 namespace·증가 순번·원본 행·방면·승차 좌표를 검사한다. 미지원/반복 정류장/
누락/선택-저장 불일치는 공급자 조회 전에 차단한다. 서버 경로 변경은 조회 전후 fingerprint로 차단한다.

이번 E2E는 **별도 합성 ODsay 메타데이터 + 기존 합성 TMAP GPS 형상**을 조합한 시험이다.
이를 실제 ODsay 도보 형상 적격성이나 native 입력과 저장 경로 전체 일치의 검증으로 승격하지 않는다.
실제 선택 경로에는 매핑 미리보기만 추가했고 LOCAL_ONLY/운영 플래그 default-off는 유지했다.
자세한 범위와 E2E 증거는 [P2-2b 검증 기록](journey-engine-p2-2b-validation.md)을 따른다.

#### P2-3a 저장 경로·상세 화면·로컬 Live Activity 첫 연결 (지원 범위 구현)

새 prepare-saved API가 본인 저장 경로와 독립 출발/도착 좌표로 native v1 입력을 재구성하여
전체 allow-list, 원문 SHA-256, 소유권·세션 generation·TTL을 검사한다. 서버 확인 후에도 native의
첫 도보 형상 검사와 simulator/SANDBOX 제한을 유지한다. 이전 companion 매핑 fixture 대신
단일 전체 합성 TMAP 저장 경로를 사용하며, 실제 공급자 ID나 도착정보를 만들어 넣지 않는다.

화면 밖 native Runtime의 동일 projection을 기존 ScheduleDetail 경로 상세 카드와 별도 로컬
ActivityKit 위젯에 표시했다. 준비만으로는 출발/Activity를 만들지 않는다. 실제 CoreLocation 이동으로
자동 출발한 뒤 첫 도보 진행·정류장 접근/대기를 표시하고, 탑승 후보/위치 만료 시 진행률을 숨긴다.
검증된 자동 안내가 연결된 상세 컴포넌트에서는 수동 출발 버튼을 숨긴다. 정상 운영 경로는 아직 자동
안내가 활성화되지 않으므로 기존 출발 흐름을 전역 삭제하지 않았다.

독립 창의 GPS → 자동 출발 1회 → 상세 타임라인/대기 → 잠금 위젯 → stale → 종료 제거를 확인했다.
시험은 기존 실제 상세 컴포넌트에 합성 previewItem을 공급한 것으로, 인증된 운영 일정 E2E나 실제
운행 정확도를 증명하지 않는다. 지도 설정은 실서버 차단으로 미표시이며 위치/경로 오버레이는 미검증이다.
실시간 현황 허용 요청은 승인 없이 남겨 두었으며, 허용 이후 지속성·실제 APNs도 미검증이다.
테스트 수치와 제한은 [P2-3a 검증 기록](journey-engine-p2-3a-validation.md)에 기록한다.

#### P2-3b1 native 도착 관측·공통 화면 연결 (지원 범위 구현)

native Runtime이 화면 마운트와 독립적으로 canonical binding을 재검증하고 버스 도착정보를 조회한다.
자동 출발 ACK 이후 신선한 GPS의 접근/대기 상태에서만 조회하며, 지원되는 저장 메타데이터만 사용한다.
원본 source timestamp/TTL, 노선·방면·원본 승차 순번, session/generation/revision/digest를 대조한다.
후보·위치 만료·응답 오류·불일치에서는 ETA를 숨기고 도착정보만으로 탑승/하차를 확정하지 않는다.

기존 상세 카드와 로컬 잠금 위젯에 같은 도착 관측을 연결했다. DEBUG simulator/SANDBOX의 고정

| P2 후속 완주 | 차량 이동 증거 결합, 승하차 확정·잔여 정류장·한 정류장 전 안내, TTS/알림 정책 | 검증된 상태부터 동일 화면에 확장 |

P2-3에 지하철·환승(P3) 전체 완료는 필요 없다. 다만 P2-2b 없이 버스 번호나 정류장 이름만으로
도착시간을 실제 선택 경로에 붙이지 않는다. 미지원 경로는 위치 진행/불확실성만 표시하고 도착 안내는 보류한다.

P2-3의 경로 상세와 Live Activity는 하나의 엔진 snapshot(session/revision/quality/phase)을 소비해야 한다.
[P2-3b2a 검증 기록](journey-engine-p2-3b2a-validation.md)은 현재 위치 표시와 상세 시험 진입의 정확한 범위를 기록한다.
[P2-3b2b1 검증 기록](journey-engine-p2-3b2b1-validation.md)은 화면 밖 서버 검증과 cold 복구의 시험 범위를 기록한다.
[P2-3b2b2a 검증 기록](journey-engine-p2-3b2b2a-validation.md)은 인증 transport와 정리 내역, 합성 JWT E2E 및 실제 인증 미검증 경계를 기록한다.
[P2-3b2b2b1 검증 기록](journey-engine-p2-3b2b2b1-validation.md)은 foreground 갱신·logout race 보호와 독립 GPS/상세/로컬 잠금 E2E, 잠금 중 갱신 미구현 경계를 기록한다.
[P2-3b2b2b2 검증 기록](journey-engine-p2-3b2b2b2-apns-validation.md)은 실제 update token 발급과 원격 전달 미검증, 사용자 전체 경로 바 요구사항을 기록한다.
[P2-3c1 검증 기록](journey-engine-p2-3c1-validation.md)은 전체 경로 바의 구간 내부 위치와 대기 경계, 상세/축소 상세/잠금 GPS E2E 및 후속 UI 범위를 기록한다.
[Live Activity 디자인 검증](journey-live-activity-design-validation.md)은 퍼센트 없는 단계·잔여 도보 거리·정류장명 표현과 독립 잠금 화면 E2E를 기록한다.
[P2-3c2a 검증 기록](journey-engine-p2-3c2a-validation.md)은 상세 React 문구·현재 타임라인 행 연결과 자동 검증 결과, 독립 화면 GPS E2E를 기록한다.
[P2-3c2b 검증 기록](journey-engine-p2-3c2b-validation.md)은 저장 원본과 검증한 노선명/색상·비례 구간 폭, metadata budget, 3구간 독립 GPS/큰 글자 E2E와 긴 경로/전체 접근성 잔여 게이트를 기록한다.

[P2-3c2b2 검증 기록](journey-engine-p2-3c2b2-validation.md)은 32구간/긴 이름 독립 GPS·로컬 잠금 시험, 확대 글자 안내 재측정·축소 요약 접근성·대비 개선과 아직 통과하지 못한 전체 페이지/VoiceOver 및 cold 종료 handoff 게이트를 기록한다.

[2026-10-06 주요 안정성 검증](journey-readiness-validation-20261006.md)은 이번 개발·자동 검사·독립 GPS cold stop/로컬 잠금 E2E와 전체 접근성/실제 APNs의 미검증 이유를 기록한다. [실기기 오류·검증 runbook](journey-device-validation-runbook.md)은 위치 단절·권한·공급자·무음/오디오·APNs·재시작/만료·긴 경로·배터리·재탐색별 재현 방법과 필요한 증거를 정리한다. 준비 문서를 현장 합격으로 간주하지 않는다.

[실제 APNs 연결 검증 2026-10-06](journey-apns-connected-validation-20261006.md)은 초기 거절 이력이다. [Sandbox 키 수정 후 재검증](journey-apns-sandbox-validation-20261006.md)은 원격 UPDATE 수신과 당시 stale 실패를 기록한다. [위치 만료·실제 END 검증](journey-apns-end-validation-20261006.md)에서 온라인 stale 제거·회복·명시 원격 END→잠금 카드 제거→재시작 미재생성을 확인했다. [종료 기록 자동 정리 검증](journey-checkpoint-reconciliation-validation-20261006.md)에서 동일 인증 terminal 자동 정리·진행 기록 보존·조회 장애 회복을 통과했다. [서버 TTL 검증](journey-server-expiry-validation-20261006.md)은 앱 미실행 만료와 cold 정리를 외부 APNs 없이 확인했다. 최신 [서버 만료→자동 END 검증](journey-expiry-auto-end-validation-20261006.md)은 메모리 시험 sender에서 실제 provider 자동 END 2회와 사용자 재진입 전 독립 잠금 카드 제거를 확인했다. 운영 worker 연결·durable token/outbox/process restart 성공은 아니다. 다음 게이트는 운영 영속 소유권/회전·terminal 전달 복원, 새 로그인 세대/실제 안내 수명, 오프라인 stale fallback·실제 망 지연 UPDATE 역전이다. 정상 로컬 종료를 원격 END 증거로 대체하지 않는다. 콘솔/키 변경은 임의로 수행하지 않는다.
각 화면이 별도로 시간을 추정하거나 단계 버튼을 통해 상태를 변경하지 않는다. 지도 진행 표시,
접근/대기 안내, stale 표시, 종료 처리는 이 공통 상태에서 파생한다.

후속 [영속 END/서버 재시작 검증](journey-durable-end-validation-20261007.md)은 이전 메모리 sender의 restart 미지원 경계를 좁혔다. main-source dispatcher는 저장 terminal과 암호화된 immutable lane을 복원한다. 격리 H2 file DB+실제 APNs restart E2E와 격리 MySQL+합성 provider 검사를 구분한다. 운영 migration/플래그는 적용하지 않았으며 token 회전/전체 실제 인증/새 로그인 회수는 여전히 열린다. 과거 표의 미완료 표시는 당시 결과다.

같은 단계의 E2E에서 발견한 정상 종료 뒤 일시 위치 오류 잔류도 수정했다. Swift 270·signed native build·config 8 PASS, 독립 창 GPS clear→ARMED의 실제 CoreLocation 오류→종료 뒤 STOPPED/오류 없음/큐 0을 재검증했다. 이 후속 검사는 provider OFF이며 앞의 실제 APNs 증거와 구분한다.

#### 남은 단계의 완료 판정

2026-10-07 사용자 요청에 따라 앞으로도 **각 구현 단계의 자동 검사→독립 시뮬레이터 GPS/UI E2E→증거 기록**을 완료한 뒤 다음 단계로 이동한다. 실패는 수정·재시험하고 합성/실제 공급자·provider 수락/화면 수신을 구분한다. 단계 일부의 성공을 P2~P4 전체 완료로 표시하지 않는다.

| 남은 축 | 현재 막힌 완료 근거 | 다음 개발/검증 |
| --- | --- | --- |
| Activity lifecycle | token 회전·새 로그인·실제 등록 DB 통합/운영 적용 | epoch 계약/인증 회수, 단위·DB 경쟁·독립 잠금 재시작 E2E |
| 실제 버스 완주 | 차량 위치/정류장 occurrence/방면 실응답·현장 탑승 표본 미확보 | 지원 노선/권한 선택, provider 관측 어댑터·자동 승하차/한 정류장 전 정책·GPS replay E2E |
| 안내 채널 | 실제 안내 이벤트 TTS/알림 연결 미완료 | 이벤트 중복/취소·사용자 음성 설정·시뮬레이터 표시 E2E, 물리 무음/가청 성공은 실기기 |
| P3 지하철/환승 | 열차/방면/정차역 관측과 터널 표본 미확보 | 보수적 위치 정책·환승별 replay E2E, 현장 유형별 검증 |
| P4 재탐색/베타 | revision 전환·잘못된 탑승/놓친 하차·장시간 품질 미완료 | 이탈/재탐색 E2E, 실기기 배터리·잠금·회수·VoiceOver |

현재 **시뮬레이터만**이라는 사용자 범위를 유지한다. 실기기/현장·새 외부 자격증명/권한·운영 DB 변경이 필요한 게이트는 별도 승인/입력 없이 우회하지 않는다. Android P5는 별도 범위 확인이 필요하다.

ActivityKit의 로컬 시작·갱신과 시뮬레이터 잠금 화면 표시는 P2-3 화면 테스트 대상이다.
실제 APNs UPDATE/END의 단일 시뮬레이터 수신은 위 범위에서 확인했다. 운영 지속성, 무음 모드 음성→알림 전환과 현장 정확도는
실기기/외부 게이트이며 시뮬레이터 성공으로 완료 처리하지 않는다.
사용자 배포는 이 게이트와 버스 한 경로 완주 검증을 모두 통과한 후 판단한다.

### P3 지하철과 환승 자동 안내

- 신선한 열차 도착정보에 따른 약 2분 전 안내.
- 지하철 탑승·이동·하차와 터널 불확실성 처리.
- 버스↔버스, 버스↔지하철, 지하철↔지하철 환승.
- 방면·분기·순환선·급행 구분, 제공되는 승강장·출구 정보 활용.
- 다음 구간 실시간 조회와 안내 채널 전환.

통과 기준: 각 환승 유형에서 실제 이동 표본 확보.
시간 경과만으로 현재 역을 확정하지 않고, 정보 부족 구간의 누락률도 측정함.

### P4 이탈 복구와 제한 베타

- 잘못된 탑승·놓친 하차·환승 실패 감지, 재탐색과 revision 전환.
- 장시간 잠금·앱 재시작·서버 장애·권한 회수·계정 전환 검증.
- 배터리·발열·데이터 사용량·제공처 quota 측정.
- 개인정보 고지, 기능별 중단 스위치, 운영 대응 절차 정리.
- 내부 검증 → 제한 TestFlight → 검증된 지역·노선부터 점진 확대.

통과 기준: 11절 출시 게이트 충족. 버스 1개 경로의 성공을 전체 기능 출시로 확대 해석하지 않음.

### P5 Android 동등 기능

iOS 정책·계약·fixture를 기준으로 Android 위치 실행부·지속 알림·TTS를 구현한다.
OS·제조사별 백그라운드 정책은 별도 확인한다. iOS 완료만으로 Android 지원을 선언하지 않는다.

일정은 P0 이후 지원 지역·필수 데이터·지원 OS·실기기 가용성에 맞춰 재산정한다.
이전 수동 파일럿 기준의 기간을 자동 내비게이션 납기로 재사용하지 않는다.
모바일은 P1 Runtime/Core, 백엔드는 실시간 어댑터·자동 관측 API를 병렬 구현할 수 있다.

## 11 검증과 출시 게이트

### 11.1 검증 단계를 구분한다

| 단계 | 검증 내용 | 대신 증명하지 못하는 것 |
| --- | --- | --- |
| 순수 엔진 테스트 | 상태 전이·관측 품질·중복 방지·replay 결정성 | 실제 GPS와 차량 판정 정확도 |
| 독립 시뮬레이터 E2E | 위치 주입→자동 상태→화면·음성 요청·복구 | 실제 터널·배터리·오디오 하드웨어 동작 |
| 실제 APNs E2E | 서버→FCM→APNs→해당 Activity 잠금 표시·갱신·종료 | 실제 탑승 판정 정확도 |
| 실기기 현장 테스트 | 실제 위치·무음·잠금·하차 타이밍·환승·장시간 동작 | 미시험 지역·노선의 동등한 품질 |

시뮬레이터는 사용자 요청대로 Device Hub 관리 화면이 아닌 별도의 독립 기기 창에서 조작한다.
실기기 위치·교통 데이터·시험용 계정과 APNs 설정이 준비되지 않은 검증은 미검증으로 표시한다.
실제 APNs 전송은 시험용 계정·기기와 개발 환경에 한정한다.

APNs는 서버의 전송 성공 응답만으로 통과하지 않는다. 동일 session/Activity에 대해
시작·갱신·종료가 잠금 화면에 반영된 시각과 내용을 증거로 남긴다.
토큰 미등록·교체·알림 거부·Live Activity 비허용·오프라인·지연·중복·역순·종료 후 전송도 시험한다.

### 11.2 필수 회귀와 품질 측정

- 출발 전 알람과 일정 출발 처리의 정확한 전환, 중복 세션·기기 소유권 충돌.
- 오프라인 자동 출발 뒤 미동기화된 서버 출발 알림, 재접속 시 중복 활성화.
- stale·낮은 정확도·역순 관측, 터널, 평행 노선, 순환선, GPS jump.
- 잘못된 탑승·하차 지나침·환승 실패·재탐색 후 과거 사건 차단.
- 재시작·재연결 시 중복 발화 방지, 종료 뒤 추적·TTS·조회 정리.
- 화면 잠금 60~90분, 무음 전환, 통화, 음악, Bluetooth·이어폰 분리.
- 위치·알림·Live Activity 권한 변경, 로그아웃·계정 교체.
- 음성 OFF에서도 위치·진행 표시가 유지되는지 확인.
- 로컬·원격 Live Activity 역전, stale 표시, 실제 APNs 지연 측정.

현장 기록에는 기준 정답, 경로·조건별 표본 수, 오탐·미탐·판정 지연·안내 시점·불확실 지속 시간을 남긴다.
안내를 억제한 사례를 분모에서 빼서 정확도가 높아 보이게 하지 않는다.

초기 품질 목표 후보는 현재 구간 판정 95% 이상, 필요한 하차·환승 안내의 행동 가능 시간 내 전달
99% 이상이다. 아직 측정값이나 보장 수치가 아니다.
P0에서 측정 방식과 조건별 최소 표본 수를 정하고 제한 베타 전에 확정한다.
위험한 오안내·이미 지난 하차 지시·종료 후 안내는 출시 차단 결함으로 다룬다.
작은 표본의 성공률만으로 목표 달성을 선언하지 않는다.

배터리는 같은 기기·경로·잠금 조건의 기준선 대비 추가 소모를 측정한다.
기존 후보인 median 5%p/h 이하·p90 8%p/h 이하도 실측 전 승인된 보장이 아니며 P0에서 재검토한다.
실측이 없으면 정확도·배터리·음성 전달 성능은 `unmeasured`로 유지한다.

## 12 개인정보 운영과 완료 정의

원시 위치는 기기 내 짧은 판정 버퍼로 최소 처리한다. 진단 trace 수집·업로드는 별도 동의와
보관 기한을 필요로 한다. 좌표·토큰·정류장명·사용자 식별자를 일반 로그나 metric tag에 남기지 않는다.
파생 여정 상태도 개인 이동정보이므로 접근 제어·보관·삭제 정책을 적용한다.
위치 사용 고지와 개인정보처리방침은 출시 전에 실제 동작에 맞게 정비한다.

관측 지표는 판정 품질, 불확실 지속, 안내 지연·억제 사유, 중복, provider 오류,
APNs 전송 단계, 배터리와 종료 정리 상태를 중심으로 제한된 enum으로 수집한다.
위치·음성·안내 알림·Live Activity·자동 출발을 개별 중단할 수 있게 하고,
활성 안내를 중단하면 사용자에게 사실을 알린다. 과거 진행을 정상 안내처럼 남겨두지 않는다.

기능 완료는 다음을 모두 만족할 때다.

- 버튼으로 단계를 넘기지 않고 출발·탑승·하차·환승·도착을 자동 판단한다.
- 지도·음성·알림·Live Activity가 같은 상태와 근거를 표시한다.
- 지원 범위의 잠금·무음 요구사항과 실제 APNs 표시 검증을 통과한다.
- 이탈·단절·데이터 지연에서 오안내 없이 복구하거나 불확실성을 명시한다.
- 실제 이동과 품질 표본을 확보하고 지원 지역·제약을 명확히 안내한다.
- 종료 후 추적과 안내가 정리되며 기존 출발 알림에 회귀가 없다.

구현은 단계별 코드·회귀 테스트·독립 시뮬레이터 E2E를 묶어 진행한다. P0 진단 화면의 시작·중지
버튼은 시험 장치의 제어이며 제품의 탑승·하차 확인 버튼이 아니다. 현재 진단 기반만으로
자동 내비게이션 구현이나 P0 전체 통과를 선언하지 않는다.
실제 공급자·APNs·실기기 검증이 남아 있어도 외부 데이터와 독립적인 P1 순수 코어·합성 replay는
개발할 수 있으나, 이를 실제 버스 탑승 검증 완료로 승격하지 않는다.
배포, 커밋·푸시, 운영 데이터 변경은 별도 요청 없이 수행하지 않는다. 기존 미커밋 작업과
원본 체크아웃을 보존하며 `.env`는 읽거나 수정·복사·커밋하지 않는다.
