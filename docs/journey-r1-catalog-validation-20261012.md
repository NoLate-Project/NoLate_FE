# R1 공식 버스 형상 매핑 보강 — 2026-10-12

전체 대중교통 내비게이션 완료 보고가 아니다. 이번 변경은 정적 노선 형상 매핑과 그 회귀 검증이다.

## 승인·실제 조회

사용자의 추가 승인 후 서울 7016 고정 노선에 대해 공식 `ws.bus.go.kr`의
`getStaionByRoute`/`getRoutePath`를 HTTP로 각 1회, 총 2회 조회했다.
재시도·리다이렉트·차량 조회·키/요청 URL 출력·`.env` 수정은 하지 않았다.
이 2회 승인은 모두 소모됐으며 새 조회에 재사용하지 않는다.

정류장 106개, 형상 1,693점이 확보됐다. 선택한 44~48번의 공개 정류장 번호는 모두
유효했지만 전체 목록의 선택 밖 1개 번호가 유효하지 않아, 기존 readiness 명령은
`DIAGNOSTIC_CATALOG_WITH_INVALID_STOP_NUMBERS`로 실패 종료했다.
이는 조회 실패나 선택 구간 번호 오류가 아니며, 전체 catalog를 무조건 정상으로 바꾸지 않았다.

추가 조회를 피하려고 공개 형상·순서만 owner-only 임시 진단 파일에 보존했다.
이 파일에는 키, URL, 원문 XML, 정류장/방면 이름, 실제 공급자 식별자, 공개 정류장 번호,
차량/사용자 GPS가 없다. 반복 정류장·방면 관계는 대체 ordinal로만 보존한다.
실제 공개 노선 좌표는 남지만 사람의 이동 기록이 아니다. repo에는 원본 진단 파일을 추가하지 않는다.

## 원인과 수정

이전 구현은 선택 구간 밖 정류장이라도 40m 오차 원 안의 연속 노선 길이가 100m를 넘으면
전체 매핑을 즉시 거부했다. 이번 응답에서 순서 98의 한 연속 통과는 약 133.2m,
순서 102의 두 통과는 약 102.1m/113.0m였다.

수정 후 선택 밖 정류장은 통과 구간 전체를 불확실한 interval로 남긴다.
전방 최소/후방 최대 도달 위치를 누적해 **모든 정류장을 빠짐없이 5m 이상 전진하는
완전한 순서 배정**이 가능한지 검사한다. 쌍마다 가능하다는 이유로 전체 불가능한 체인을
통과시키지 않는다. 선택 정류장은 기존의 bounded projection 자체가 전후로 도달 가능해야
하며, 가능한 통과가 하나뿐이어야 한다.

- 선택 정류장의 100m 초과 통과는 여전히 차단한다.
- 선택 구간의 반복/평행 노선 후보는 여전히 모호하면 차단한다.
- 40m 오차·5m 전진·후보 개수·좌표/정류장/형상 입력 한도는 완화하지 않았다.
- 선택 밖 정류장을 삭제하거나 가까운 점 하나로 임의 고정하지 않는다.
- 정적 매핑 성공은 차량 연결·탑승 확정·실제 도보 연결 성공이 아니다.

## 오프라인 실제 응답 재검증

`seoulBusCatalogOfflineReplay`는 test source에만 있으며 HTTP client/자격증명/앱/DB/APNs를
사용하지 않는다. 지정된 진단 파일과 schema/필드/자료형/크기/진단 전용 표식을 검사하고,
공급자 ID 대신 합성 식별자를 재구성해 실제 matcher를 실행한다.

같은 응답에서 `MATCHED`, 선택 순서 `[44,45,46,47,48]`, 다섯 개 projection을 얻었다.
추가 네트워크 요청은 0회다. `navigationReady=false`,
`stopSectionCrosswalkVerified=false`, `passengerVehicleAssociation=false`는 그대로다.
실제 저장 ODsay 경로/도로 section/실시간 차량과의 end-to-end crosswalk 통과로 확대하지 않는다.

## 독립 시뮬레이터 E2E 실행 기록

대상은 `NoLate R2 Session E2E 20261008` / iOS 26.5 / 분리된
`deviceWindow-AppWindow-9` 창이다. 툴바 `Show in Device Hub`로 분리 상태를 확인했고
Hub 내부 미리보기 대신 해당 독립 화면을 조작했다. 실기기는 사용하지 않았다.

7016 진단 자료를 실제 저장 경로로 위장하지 않는다. test-source harness에 별도 opt-in
`NOLATE_JOURNEY_TEST_CATALOG_BEND=1`을 추가해 합성 WALK-BUS-WALK의 **선택 밖**
정류장에 긴 연속 굽은 통과를 만들었다. 서버의 실제 mapping 코드를 통과한 바인딩을
native에 전달하고 CoreLocation 좌표와 독립된 합성 차량 시계로 시험한다.
단계/탑승/하차/도착을 강제하는 버튼은 사용하지 않았다.

첫 실행: 바인딩/ARMED→GPS 출발→상세 도보 현재 행·마커→잠금 정류장 대기까지 확인했다.
그러나 이후 탑승 근거가 누적되지 않아 완주 실패했다. 위치 불확실 시 마커가 숨겨졌고
수동 시험 종료 후 서버 STOPPED/종료 큐 0을 확인했다. 합격으로 덮어쓰지 않는다.
동시에 첫 Metro에서 Watchman 오류로 프로세스가 종료된 것을 확인했다. 이것이 탑승 실패의
원인이라는 인과관계는 아직 증명되지 않았다. 재시험에서는 기존 QA 옵션으로 Watchman을
사용하지 않고, 승차 후보 phase/reason/근거 수/GPS 오차 진단을 내부 화면에 추가했다.

두 번째 실행: 전경에서 동일 GPS replay로 ARMED→자동 출발→승차 후보→차량 동행
근거 4개/RIDING을 확인한 후 상세 화면과 잠금 화면을 교대로 확인했다.
버스 현재 마커/다음 정류장·약 230m 하차 준비→잠금 목표 정류장 근접→차량 분리 이후
최종 도보 현재 행·마커(약 80m→50m)→잠금 도보 20m→목적지 연속 체류 후 카드 제거를
확인했다. 단계 전환이나 도착 종료 버튼은 누르지 않았다. 마지막 native 상태는
STOPPED/목적지 도착/출발 1/알림 접수 5/음성 큐 0/오류 없음/서버 종료 대기 0/남은 기록 없음이었다.
콜드 재시작에서는 IDLE/OFF/접수 0/음성 큐 0/종료 대기 0/남은 기록 없음을 AX로 재확인했다.

서버 최종 누적 계수는 준비/출발/활성화/기존 출발 작업 취소 각 2,
rejected/trap/실제 APNs 수락 각 0, 마지막 상태 STOPPED였다. 이 2회에는 첫 실패 실행도
포함되며 두 완주 합격으로 계산하지 않는다. replay는 정상 완료 후 GPS 주입을 해제했다.
출발 전/승차 전 조기 잠금 상태에서의 탑승 재현 안정성은 이번 결과만으로 해소됐다고 하지 않는다.

두 번째 Metro에도 listener/handler-only Expo 동적 import의 경로 해석 경고가 있었다.
별도 알림의 전경 표시 경로를 조사할 단서지만, 잠금 알림 미표시의 원인으로 확정하지 않는다.
기존 알람/UN delegate를 전역 교체하거나 `node_modules`를 임의 수정하지 않았다.

화면 증거는 [evidence 디렉터리](evidence/journey-r1-catalog-20261012/)에 보존한다.
별도 안내 알림 접수는 실제 잠금 알림 표시/청취 합격이 아니다. 이번 실제 APNs 전송은 0건이다.

시험 종료 후 대상 앱·GPS와 이번 8088 Metro/15544 harness만 정리한다.
원본 `.env`, 운영 설정, 실기기, 다른 시뮬레이터·서버는 바꾸지 않는다.
